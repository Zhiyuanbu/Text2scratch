This page is intentionally plain. It is the machine-readable technical reference for text2scratch syntax and command generation.

1. System overview

text2scratch converts plain-text commands into Scratch 3 project data.

Primary outputs:
- .sb3: a standard Scratch project archive
- .t2sh: a text2scratch session archive for fast restore

Primary workflow:
1. Write setup commands, stage code, and sprite code in text form.
2. Validate structure and command compatibility.
3. Export to .sb3 or .t2sh.
4. Optionally save or share through the cloud workspace.

Source of truth for commands:
- ../blocks.json

Use this page when you need:
- exact syntax rules
- project structure requirements
- target compatibility rules
- command metadata in deterministic form
- implementation notes for AI or automation workflows

2. Exact syntax rules

- Use one command per line.
- Nested control blocks must end with a matching line containing only: end
- else may only appear inside an if or if_else block and before the matching end.
- Strings with spaces should use double quotes.
- Expressions start with @ and are used inside other commands, not as standalone lines.
- Reporter and boolean commands usually use function-style syntax such as:
  @var(score)
  @gt(@var(score), 5)
  @join("Level ", @var(level))
- Stage logic belongs under: stage_code =
- Sprite logic belongs under:
  sprite = "Name"
  name_code =
- Setup commands such as make_var, make_list, and make_broadcast should appear before scripts when possible.
- Shared projects opened from a share link are read-only until forked into a personal editable copy.

3. Required project structure

Recommended file layout:

make_var score 0
make_broadcast round_start

stage_code =
  when_flag_clicked
  broadcast round_start
end

sprite = "Cat"
cat_code =
  when_broadcast_received round_start
  move 10
end

Notes:
- stage_code = starts stage scripts.
- sprite = "Name" declares a sprite section.
- the matching script section is lower-case sprite name + _code =
- multiple sprite sections are allowed.
- additional sprite metadata such as svg = "..." may appear after sprite declaration.
- missing end lines will block export.

4. Correct vs incorrect patterns

CORRECT
set_var score @add(@var(score), 1)
if @gt(@var(score), 3)
  say "Ready"
end

INCORRECT
@add(1, 2)
@var(score)

CORRECT
stage_code =
  when_flag_clicked
  switch_backdrop_to backdrop1
end

INCORRECT
stage_code =
  when_flag_clicked
  move 10
end

CORRECT
sprite = "Ball"
ball_code =
  forever
    move 5
  end
end

INCORRECT
sprite = "Ball"
forever
  move 5
end

5. Common mistakes and edge cases

- Missing end after repeat, forever, if, if_else, or repeat_until.
- Using reporter or boolean expressions as their own lines.
- Using sprite-only commands in stage_code.
- Forgetting to declare a sprite before its sprite_code section.
- Guessing menu values instead of using allowed dropdown values from blocks.json.
- Mixing up .sb3 and .t2sh: .sb3 is for Scratch, .t2sh is for text2scratch restore.
- Opening a shared project and expecting direct editing: shared loads are read-only until forked.
- Assuming aliases exist for every command. Only aliases listed in blocks.json are guaranteed.
- Using unsupported or misspelled command names instead of the exact syntax form.

6. Implementation notes

- The browser app uses the generated command catalog bundle first and falls back to ../blocks.json when needed.
- The converter UI lives on ../converter.html and is powered by ../app.js.
- The search reference UI lives on ../reference.html and is powered by ../docs.js.
- Auth and cloud save are optional and use Supabase from the browser.
- Shared project URLs should resolve to the converter workspace with a share query parameter.
- The safest command-generation strategy is:
  1. choose exact syntax from blocks.json
  2. keep one command per line
  3. place expressions only inside inputs
  4. close every open control block with end
  5. respect stage vs sprite compatibility
